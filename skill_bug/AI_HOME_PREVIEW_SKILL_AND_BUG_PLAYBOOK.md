# AI 家居空间预览项目：Skill 与 Bug 实战手册

本文面向后续接手该项目的 AI 或工程人员。它不是某一次修改记录，而是一套可复用的判断方法：如何维护“对话式场景生图”产品，如何避免把生成流程退化为前端拼贴，如何保证任务、图片和历史对话正确归属，以及如何定位异步模型接口中的长耗时和部分失败。

## 1. 项目定位与当前基线

产品目标是：用户上传真实空间图片和商品参考图，通过自然语言和点选位置，把商品自然地加入或替换到原场景中。结果应保留原场景结构、机位、构图、纹理和未编辑物体，并让新增物体具备合理尺寸、透视、接地、遮挡、阴影与局部光照。

当前冻结基线：`V2_test`。

- 线上地址：<https://qijing-ai-home-preview.mawellhihi.chatgpt.site/>
- 基线提交：`7f9f3c03d1ac6b652aa9a8c649168660a821e882`
- 归档目录：`../V2_test/`

后续开发前，应先确认当前工作目录与 `V2_test` 的差异，不要直接修改冻结目录。

## 2. 核心架构认知

### 2.1 前端与服务端职责

前端负责：

- 上传并保存用户最初的空间图、商品图。
- 记录原始宽高、宽高比和来源类型。
- 把点选坐标保存为归一化比例。
- 固定任务创建时的对话、场景、基础图片和 Prompt 版本。
- 展示阶段状态、最终结果、历史对话、引用关系和管理员记录。
- 轮询异步图片任务，但不在浏览器进行商品抠图叠加。

服务端负责：

- 调用视觉模型进行需求和空间解析。
- 调用图片编辑模型完成 Round 1、Round 2。
- 调用视觉模型执行 Round 3 质量检查。
- 返回真实模型请求 ID、图片 URL、状态和错误。

关键原则：浏览器只能提供展示和任务编排，不能把“抠图后叠加到 canvas”伪装成 AI 场景编辑结果。

### 2.2 当前生成管线

| 阶段 | 是否生图 | 目标 |
|---|---:|---|
| Round 0 需求解析 | 否 | 解析操作、素材、位置、尺寸、冲突、空间与支撑面 |
| Round 1 基础生成 | 是 | 完成添加/替换，优先保证商品、位置、房间结构 |
| Round 2 综合修正 | 是 | 修正比例、透视、接地、遮挡、穿模、阴影、光照、色温、背景漂移 |
| Round 3 质量检查 | 否 | 对照输入与 Round 2，输出 PASS/FAIL 和问题说明 |

首次 QC 为 FAIL 时，只允许一次局部纠错和复检。不得无限重试。

## 3. 高价值 Skill：可复用的工程方法

### Skill A：把生成任务当作不可变快照

任务创建瞬间固定以下字段：

- `task_id`
- `conversation_id`
- `scene_id`
- `base_image_id`
- 基础图原始来源
- 商品参考图
- 操作类型
- 点选位置
- 尺寸
- 用户文字指令
- `prompt_version`

结果写回时只使用任务快照中的 `conversation_id`，绝不能读取“生成完成时当前打开的对话”。

泛化价值：任何异步 AI 任务都不应依赖完成时的 UI 当前状态。用户可能切换页面、打开历史记录或新建会话；任务归属必须由创建时快照决定。

### Skill B：区分展示图片与模型原始输入

页面可以使用固定容器、缩略图或响应式布局，但模型输入必须优先使用原始上传文件或历史生成的原始 URL。

禁止：

- 截取聊天框 DOM 再送入模型。
- 使用 `html2canvas` 生成基础图。
- 因预览容器而执行 center crop。
- 把 `object-fit: cover` 的视觉裁切当作真实图片数据。
- 把固定 canvas 尺寸输出当作用户原图。

必须记录：

```text
original_width
original_height
aspect_ratio
source_kind
```

如果接口要求固定尺寸，采用等比例缩放和 padding/letterbox，优先选择接近原始比例的输出规格，不直接裁切主体。

### Skill C：用归一化坐标隔离 UI 尺寸变化

点选时记录：

```text
x_ratio = (clickX - displayedImageLeft) / displayedImageWidth
y_ratio = (clickY - displayedImageTop) / displayedImageHeight
```

生成或空间分析时再映射：

```text
originalX = x_ratio * original_width
originalY = y_ratio * original_height
```

不要直接保存 CSS 像素。点击应以真实可见图片边界为坐标系，而不是外层留白容器。

泛化价值：任何在缩略图、画布或响应式图片上标注位置的产品，都应把界面坐标转换为与原始媒体无关的归一化坐标。

### Skill D：对部分成功进行降级，而不是抹掉成果

该管线可能出现：Round 1 成功、Round 2 成功、Round 3 QC 服务失败。

正确处理：

- 保留 Round 2 图片。
- 前台正常展示、引用和下载。
- 标记 `QC 待确认`。
- 管理员后台记录 Round 3 `UNAVAILABLE`、错误和 request ID。
- 只重试 QC，不重复消耗两轮生图。

错误处理不能简单地写成“任何后续异常都让整个任务失败”。应先判断是否已经产生可用、可追踪的中间产物。

泛化价值：视频渲染、文件转换、数据流水线、Agent 工作流都需要“阶段级成功”和“可恢复检查点”，而不是只有全成功/全失败。

### Skill E：管理员后台展示真实链路

管理员后台不能展示前端模拟进度或静态示例。每个阶段至少记录：

```text
name
state
start_time
end_time
duration
request_id
prompt
prompt_version
last_updated_at
input summary
output summary
image_url（生图轮次）
error / QC data（非生图轮次）
```

历史任务必须保存当时使用的 Prompt 快照。更新 Prompt 模板后，不得反向修改历史任务内容。

### Skill F：Prompt 约束应围绕局部编辑

Round 1 与 Round 2 的 Prompt 应明确：

- preserve original room appearance
- preserve camera angle and perspective
- preserve original wall/floor texture
- preserve exposure and image grain
- preserve unedited objects
- do not beautify or smooth the background
- do not apply global soft light or global recoloring
- match product appearance
- realistic scale, perspective, grounding, shadow and lighting
- correct occlusion; no penetration or floating
- REPLACE only removes the explicitly replaced object

仅允许在编辑物体的边缘、接触面和投影范围做局部融合。Prompt 只是管线的一部分；如果底层接口仍是抠图叠加，增加这些文字不会把合成自动升级为场景编辑。

### Skill G：等待体验显示阶段，不伪造百分比

图片任务是异步的，模型端通常不给精确进度。因此前台应显示阶段：

1. 正在理解需求
2. 正在生成基础效果
3. 正在优化空间与光影
4. 正在检查结果
5. 完成

不要根据固定计时器展示“73%”之类的伪实时百分比。可以展示“模型排队中”“已等待约 N 分钟”，但必须与真实状态一致。

## 4. 重要 Bug 案例与泛化结论

### Bug 1：结果写入错误的历史对话

症状：用户生成期间切换对话，结果出现在完成时打开的对话中。

根因：回调读取全局 `currentChatId`，而不是任务创建时的 `conversation_id`。

修复原则：创建任务时冻结上下文；写回时通过固定 ID 找到对应对话数据和 DOM 快照。

防回归检查：启动任务后立刻切换到另一历史对话，完成后检查结果只出现在原对话。

### Bug 2：新对话继承上一对话内容

症状：点击“新对话”后，聊天内容和素材仍属于上一主题。

根因：只新增左侧列表项，没有把当前状态归档并初始化新的会话状态。

修复原则：新对话必须创建新的 `conversation_id`、`scene_id`、`base_image_id`，清空消息、引用、素材和版本计数，同时保留旧对话快照。

### Bug 3：引用历史效果图后接口 `Failed to fetch`

症状：普通文字调整可用，引用历史生成图并添加新商品时失败。

根因类型：历史图可能只剩缩略图、DOM 截图或不可再次读取的临时来源；也可能没有保存原始生成 URL 与图片元数据。

修复原则：引用时使用 `resultImages[version]` 对应的原始生成 URL，并把 `base_image_id`、原始元数据一起放入任务快照。不要重新截图聊天卡片。

### Bug 4：Round 2 已生成，QC 500 导致前台无图

症状：管理员后台可看到 Round 2，前台只显示整个任务失败。

根因：Round 3 质检异常被最外层 `catch` 捕获，并把整个任务标为 `Failed`。

实际错误示例：

```text
500 / 50002
InternalError.Algo.ModelServingError
Internal Error calling model processing
```

修复：

- 质检 500 单独自动重试一次。
- 仍失败则创建 `UNAVAILABLE` 的 Round 3 记录。
- `qc.incomplete = true`。
- 任务状态为 `QC unavailable`，而不是 `Failed`。
- 正常调用结果落地逻辑展示 Round 2。
- 对已有同类历史失败记录，仅在“存在 Round 2 图片且错误明确匹配质检 500”时做定向恢复。

泛化结论：异常边界应按阶段划分。验证器、审核器或后处理服务失败，不应自动否定已经成功产生的核心产物。

### Bug 5：一次任务耗时超过 1000 秒

症状：后台显示总耗时超过 1000 秒。

检查结果：最新任务的一个图片阶段在生产日志中至少轮询 99 次，已可见时间约 508 秒；Round 1 和 Round 2 串行执行，因此两轮均长时间排队时，总耗时可超过 1000 秒。Round 3 质检仅约 11 秒。

这不是前端虚构的百分比，也没有证据表明发生无限重试。主要原因是百炼异步图片任务长时间处于处理中。

当前实现每个图片阶段最多轮询 150 次。未来可优化：

- 把“排队时间”和“模型处理时间”分开记录（如果接口提供）。
- 设置产品级单轮超时，但不要在后台任务仍运行时盲目重复提交。
- 允许用户离开当前对话，任务在后台继续。
- 超过阈值后显示“模型排队中”，而不是让用户误以为页面卡死。
- 增加任务取消前的状态确认，避免重复计费。

### Bug 6：商品图被前端直接叠加

症状：商品背景、页面文字甚至商品截图边框进入效果图，家具透视和阴影明显不真实。

根因：使用前景分割或 CSS/canvas overlay 作为最终结果。

修复原则：房间图作为主编辑图，商品图只作参考，由 image edit/inpainting 模型重新生成局部区域。前景分割最多用于辅助蒙版，不能成为最终渲染路径。

### Bug 7：图片被固定比例裁切

症状：进入生成后，原图左右或上下区域丢失。

常见根因：

- 从页面预览区截图。
- `canvas.width/height` 固定后直接 `drawImage` 填满。
- `object-fit: cover` 的显示结果被误当输入。
- 固定 1024×1024 或横版尺寸执行 center crop。

修复原则：展示裁切和模型输入必须完全分离；原始数据保持完整宽高比，固定规格只做 letterbox 或等比例缩放。

## 5. 诊断顺序

遇到“生成失败、太慢、结果错位或历史异常”时，建议按以下顺序检查：

1. 前台任务卡：确定失败阶段，是解析、生图、轮询、QC 还是结果落地。
2. 管理员后台：核对各轮真实图片、开始/结束时间、Prompt 版本和 request ID。
3. 浏览器本地任务记录：确认任务快照、对话归属、基础图 ID 和 checkpoint。
4. Worker 生产日志：检查路由、HTTP 状态、单次 wall time、轮询次数和请求时间序列。
5. 百炼错误信息：区分 4xx 输入问题、5xx 模型服务问题、异步任务失败和前端网络错误。
6. 代码异常边界：确认失败是否被错误地扩大为整个任务失败。

不要只看前台一句“Failed to fetch”就判断模型没有调用；也不要只看 HTTP 200 就认为生图已完成。异步接口的 HTTP 200 可能只表示提交或查询成功，真实状态还要看 `task_status`。

## 6. 修改时必须保持的产品不变量

后续 AI 修改任何功能前，应检查这些不变量：

- 不使用前端叠加图作为最终结果。
- 不裁切用户原始基础图。
- 历史引用使用原始生成文件。
- 点选使用归一化坐标。
- 任务结果写回创建时所属对话。
- 新对话与旧对话状态隔离。
- Prompt 更新不改变历史任务快照。
- 两轮实际生图；QC 不生图。
- 自动纠错最多一次。
- QC 服务异常不丢弃 Round 2。
- 删除一个历史对话不影响其他对话。
- 运行时密钥不进入源码、归档或文档。
- `V1_test1`、`V2_test` 等基线目录不得被后续开发覆盖。

## 7. 最小回归测试清单

### 页面与素材

- HTML/线上页面正常打开，无 JavaScript 语法错误。
- 按钮、标签页、上传控件可用。
- 缺少空间图、商品图、点选或指令时有明确提示。
- PNG/JPEG/WebP 上传正常；原始宽高比和尺寸元数据正确。

### 生成与结果

- 点击生成后真实调用服务端接口。
- 显示真实阶段状态，不显示虚假百分比。
- 管理员后台出现 Round 1、Round 2 两张真实过程图。
- Round 3 只记录 QC，不产生第三张图片。
- 成功后前台展示真实结果并可下载。
- 结果可引用并继续编辑。

### 失败与恢复

- Round 1 或 Round 2 失败：显示失败信息和“重新生成”。
- 重试沿用原任务素材、操作、位置、尺寸和文字指令。
- Round 3 500：自动重试一次，仍失败则展示 Round 2，标记 `QC 待确认`。
- 真正缺少 Round 2 时不得伪造或恢复图片。

### 会话与归属

- 生成期间切换历史对话，结果仍回到原对话。
- 新建对话不会继承旧内容。
- 删除当前对话后切换到最近可用对话；无记录时进入空状态。
- 有运行中任务的对话不允许删除。

### 空间编辑质量

- 点选位置与文字冲突时询问以哪个为准。
- 轻微不合理落点自动纠正；明显不合理时提示确认。
- 商品尺寸、透视、接地、遮挡、阴影合理。
- 未编辑背景不过度美化，不全局柔光或调色。
- REPLACE 只删除目标家具，合理保留附近独立小物品。

## 8. 交接建议

接手新需求时先判断它属于：

- UI 展示问题
- 本地会话状态问题
- 异步任务编排问题
- 模型调用问题
- Prompt/视觉质量问题
- 部署与运行时配置问题

只修改与需求直接相关的层。比如“QC 失败后前台无图”是任务编排和异常边界问题，不应通过修改 Prompt、重新设计界面或增加第三轮生图来解决。

提交前至少执行：

```bash
node --check dist/app.js
node scripts/build-worker.mjs
node scripts/validate-worker.mjs
git diff --check
```

如果改动线上网站，应在构建、提交、发布后确认部署成功；如果用户只要求诊断，不要擅自修改或发布。

## 9. 安全与成本意识

- 不在日志、文档和聊天回复中重复显示完整 API Key。
- 不因一次轮询超时就自动重新提交图片任务，避免双重计费。
- 任何自动重试都要有明确次数上限。
- 发布前保持现有访问范围，不擅自改为公开。
- 保留用户历史数据时，不通过清空 `localStorage` 解决状态问题。
- 删除历史对话前确认没有运行中任务，并只删除该对话关联的数据。

这套方法可以泛化到其他“多阶段 AI 媒体生成 + 对话历史 + 异步任务 + 人工可检查后台”的产品：冻结任务上下文、保留原始素材、记录阶段级事实、允许部分成功、限制重试、区分展示与真实输入，并用可追踪的 request ID 和时间线进行诊断。
